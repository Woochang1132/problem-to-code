# ABR·LL-HLS 경험을 복원하기 위한 메모

이 문서는 기억을 확인하기 위한 기술 배경입니다. 아래 파이프라인과 옵션을 당시 직접 구현했다고 확정하지 않습니다. 공개 사례는 `src/data/cases.ts`의 `abr-quality-cap`입니다.

## 지금 확인된 내용

- hls.js 기반 ABR 적용, 1080p 구성의 미디어 서버 처리 부담 증가.
- LL-HLS 환경에서 방송과 시청 화면 사이 지연이 약 2.5초 → 3.5~4초로 증가. VOD 재생 시작 대기 시간과 다른 지표입니다.
- 저사양 환경에서 발열·화면 튕김 관찰.
- 최대 720p와 비트레이트 상한을 두고 고화질(720p)·저화질(당시 표기 320p)·자동 선택 제공.
- 제한 뒤 방송-시청 지연은 3.5~4초에서 약 2.5초 수준으로 안정화. 발열·화면 튕김도 감소했습니다. 약 2.5초는 당시 관찰값이며 반복 측정 분포는 미확인입니다.
- 상한이 약 1.5Mbps였다는 기억은 미확정입니다. 목표 평균 비트레이트인지 최대 비트레이트인지, 영상만인지 오디오를 포함한 값인지 구분해야 합니다. Mbps는 초당 메가비트이며 MB/s와 다릅니다.

## 서버에서 했을 수 있는 일

일반적인 구성은 입력 수신 → 디코딩 → 화질별 크기 조정 → 화질별 인코딩 → LL-HLS 패키징 → Origin/CDN 전달입니다. 입력이 이미 필요한 화질·코덱이면 일부 단계를 생략할 수 있습니다. ABR 단계가 많아지면 여러 출력을 만들어야 하므로 인코딩 자원과 저장·전송 부담이 늘 수 있습니다.

| 기억을 확인할 부분 | 설정·자료에서 찾을 단서 | 의미 |
|---|---|---|
| 1080p 출력 생성 자체를 없앴는가 | 서버 출력 프로파일, 인코딩 작업, FFmpeg 출력 매핑 | 해당 출력의 처리 부담을 줄일 수 있음 |
| 플레이어에서만 고화질을 숨겼는가 | 화질 메뉴, `autoLevelCapping`, 수동 레벨 선택 | 재생 측 선택은 제한되지만 서버 인코딩은 계속될 수 있음 |
| 실제 저화질 해상도는 무엇인가 | m3u8 `RESOLUTION`, 미디어 메타데이터 | UI의 320p 표기와 실제 영상 크기를 대조 |
| 비트레이트 상한을 어디에 두었는가 | 인코더 프로파일, `-b:v`, `-maxrate`, `-bufsize` | 인코딩 비트레이트 정책을 확인 |
| 여러 화질의 전환 경계를 맞췄는가 | GOP, 키프레임, 세그먼트 타임라인 | 화질을 바꿀 때 재생이 이어질 수 있는 구성인지 확인 |
| 저지연 처리는 무엇이 했는가 | 사용한 미디어 서버·패키저, m3u8의 `EXT-X-PART`·`EXT-X-SERVER-CONTROL` | LL-HLS 제공 경로와 버퍼·hold-back 정책을 확인 |

FFmpeg를 사용했다면 크기 조정 필터나 출력 해상도, 인코더와 프리셋, 프레임률, GOP, 비트레이트 제어 옵션을 확인하면 됩니다. `-b:v`는 목표 비트레이트, `-maxrate`와 `-bufsize`는 인코더의 비트레이트·VBV 버퍼 제어와 관련됩니다. 실제 동작은 인코더와 설정에 따르며, 네트워크의 모든 순간 전송 속도를 엄격히 제한하는 것과 같지 않습니다.

m3u8의 `BANDWIDTH`는 플레이어가 선택에 사용하는 스트림 대역폭 정보입니다. 이 값만 낮춰 쓴다고 실제 영상 비트레이트가 낮아지지는 않습니다. 같은 720p라도 코덱·프레임률·영상 복잡도에 따라 필요한 비트레이트가 다릅니다.

FFmpeg의 `-lhls`와 Apple LL-HLS를 혼동하지 않아야 합니다. 당시 사용한 패키저·미디어 서버의 LL-HLS 구현을 확인한 뒤 명령을 복원하세요.

## 플레이어에서 했을 수 있는 일

- m3u8의 화질 목록을 읽어 720p·저화질 인덱스를 확인하고 메뉴에 연결.
- 자동에서는 `currentLevel = -1`로 ABR을 사용하고, 자동 상한은 `autoLevelCapping`으로 지정하는 방식 검토.
- `autoLevelCapping`은 자동 선택 상한이므로, 수동 선택 메뉴와 서버가 노출하는 화질도 별도로 맞춰야 함.
- `lowLatencyMode`만 켜는 것으로 전체 송출 경로가 LL-HLS로 바뀌지는 않음. 서버·패키저·CDN의 지원도 필요.
- 선택 단계, 버퍼 상태, 드롭 프레임, 재버퍼링, 오류 로그를 모으면 네트워크와 단말 처리 문제를 분리하기 쉬움.

이 중 무엇을 실제로 변경했는지 당시 코드와 비교하면 기여 범위를 구체화할 수 있습니다.

## 성과 수치를 보완할 기록 틀

| 지표 | 제한 전 확인 내용 | 제한 후 확인 내용·보완할 기록 |
|---|---|---|
| 방송-시청 지연 | 기존 약 2.5초, 고화질·LL-HLS 구성에서 약 3.5~4초 | 약 2.5초 수준으로 안정화. 반복 측정한 중앙값·상위 지연 보완 |
| 화면 튕김 | 저사양 환경에서 발생 | 같은 기기에서 N회 또는 N분당 발생 횟수 |
| 발열 | 저사양 테스트 중 관찰 | 같은 재생 시간·환경의 온도 또는 일관된 관찰 기준 |
| 서버 처리 부담 | 고화질 구성에서 증가 관찰 | 동시 방송 수가 같은 조건의 CPU/GPU·인코딩 처리 속도 |
| 비용 | 부담 증가에 대한 경험 설명 | 동일 사용량·기간의 실제 비용 |

제한 후 수치를 추측해 실측 성과로 작성하지 않습니다. 측정 조건이 다르면 별도로 적습니다. 화면 튕김은 재생 오류·탭 종료·앱 종료 등 실제 현상을 구분해 기록합니다.
