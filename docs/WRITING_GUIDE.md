# 실제 경험으로 바꾸는 순서

담당 범위는 사용자 설명에 근거한 프론트엔드, 화면 설계, 모바일 설계, Player 연동, Canvas 수정입니다. 실제 장애 상황과 해결 방식은 아직 확인되지 않아 모든 사례를 작성 예시로 표시했습니다.

1. `src/app/page.tsx`에 담당 기간과 팀 구성, 구체적 기여 범위를 보완합니다.
2. `src/data/cases.ts`에서 실제 경험과 일치하는 사례만 남깁니다.
3. `problem`에 재현 조건과 사용자 영향을 씁니다.
4. `investigate`에 실제 로그, 관찰, 기각한 가설을 씁니다.
5. `options`와 `decision`에 당시 제약과 선택 이유를 씁니다.
6. `code`를 공개 가능한 실제 코드로 바꾸고, `evidence`에 실제 커밋이나 검증 자료를 연결합니다. 현재 근거 목록은 텍스트입니다.
7. 결과 섹션을 실제 관찰과 측정 조건으로 수정합니다. 하지 않은 검증은 계획으로 남깁니다.
8. 근거를 채운 사례에 한해서 작성 예시 표시를 변경합니다.

## 사실과 가정의 경계

- 원본 설계: 토큰 발급·갱신, WebRTC/HLS 경로, 방송 대기·재할당, 여러 녹화 파일, 플레이어 재생목록, 녹화정보.
- 본인 확인: 프론트 영역, 화면·모바일 설계, Player 연동, Canvas 수정 담당.
- 추가 제안: Player 상태 머신·전환 세대, SDK 어댑터, 정규화 Canvas 좌표, DPR 상한, 안정적 녹화 ID 기반 선택. 실제 구현했다고 단정하지 않습니다.
- Canvas의 실제 용도는 미확인입니다. 현재는 영상 위 오버레이를 가정하며, 실제 용도에 맞게 바꾸세요.
- 원본의 물음표 있는 정책과 HTTP 코드 의미 차이는 확정하지 않습니다.
- 도표는 담당 영역을 중심으로 재구성한 개념도입니다. 실제 네트워크 토폴로지와 다릅니다.
- 차트는 RGBA 픽셀 버퍼 계산 예시이며 실제 메모리 또는 프레임 성능 측정값이 아닙니다.

## 결과 기록 틀

| 항목 | 기록할 내용 |
|---|---|
| 환경 | 브라우저·OS·모바일 기기·SDK 버전·DPR |
| 재현 | 입력, 전환 순서, 회전/리사이즈 조건 |
| 관찰 | 이벤트 로그, 화면 영상, 좌표 값, 프레임 시간 |
| 변경 | 본인이 수정한 부분과 커밋 |
| 결과 | 같은 조건의 전후 결과와 실패 사례 |
| 한계 | 검증하지 않은 기기와 추가 비용 |

원본 설계 파일·회사 내부 코드·비공개 URL은 저장소에 복사하지 않았습니다. 실제 증거를 추가할 때 공개 가능한 범위를 확인하세요.
