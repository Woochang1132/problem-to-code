# 실제 경험으로 바꾸는 순서

담당 범위는 사용자 설명에 근거한 프론트엔드, 화면 설계, 모바일 설계, Player 연동, Canvas 수정입니다. Player 상태 전환 사례는 작성 예시입니다. ABR 사례는 1080p 구성의 부담과 지연·기기 증상을 경험한 뒤 최대 720p와 비트레이트 상한으로 서비스한 기록입니다. VOD 사례는 본인이 확인한 단일 TS + HLS BYTERANGE 전환 경험으로 교체했습니다. FFmpeg 설정 변경과 플레이어 연동을 직접 담당했으며, 당시 재생 대기 시간은 8초에서 3초로 개선됐습니다. 측정 환경과 반복 횟수는 미확인입니다.

1. `src/app/page.tsx`에 담당 기간과 팀 구성, 구체적 기여 범위를 보완합니다.
2. `src/data/cases.ts`에서 실제 경험과 일치하는 사례만 남깁니다.
3. `problem`에 재현 조건과 사용자 영향을 씁니다.
4. `investigate`에 실제 로그, 관찰, 기각한 가설을 씁니다.
5. `options`와 `decision`에 당시 제약과 선택 이유를 씁니다.
6. `code`를 공개 가능한 실제 코드로 바꾸고, `evidence`에 실제 커밋이나 검증 자료를 연결합니다. 현재 근거 목록은 텍스트입니다.
7. 결과 섹션을 실제 관찰과 측정 조건으로 수정합니다. 하지 않은 검증은 계획으로 남깁니다.
8. 근거를 채운 사례에 한해서 작성 예시 표시를 변경합니다.

## 사실과 가정의 경계

- 원본 설계: 토큰 발급·갱신, WebRTC/HLS 경로, 방송 대기·재할당, 여러 녹화 파일, 플레이어 재생목록, 녹화정보.
- 본인 확인: 프론트 영역, 화면·모바일 설계, Player 연동, Canvas 수정 담당.
- 추가 제안: Player 상태 머신·전환 세대, SDK 어댑터. 실제 구현했다고 단정하지 않습니다.
- VOD 확인: 6초 HLS 구간으로 늘어난 TS 파일 관리 부담, 단일 TS + HLS BYTERANGE 전환, FFmpeg 설정 변경과 플레이어 연동 담당, 재생 대기 시간 8초 → 3초.
- VOD 보충: 공개된 FFmpeg 명령과 m3u8·HTTP 예시는 기술 설명용이며 당시 명령을 복원한 것이 아닙니다. DB 수정 담당, 파일 감소 수, 측정 환경, 평균·분위수, 대안별 실험은 확인되지 않았습니다.
- 6초는 변환 소요 시간이나 실제 버퍼 대기 시간이 아닌 HLS 구간 목표 길이로 씁니다. BYTERANGE 자체의 성능 향상을 보장하거나 8초 → 3초를 단일 원인의 효과로 단정하지 않습니다.
- ABR 확인: 1080p 구성의 서버 부담, LL-HLS 환경의 방송-시청 지연 약 2.5초 → 3.5~4초, 저사양 발열·화면 튕김. 최대 720p와 비트레이트 상한 적용 후 방송-시청 지연 3.5~4초 → 약 2.5초로 안정화, 발열·화면 튕김 감소. 고화질(720p)·저화질(당시 표기 320p)·자동 선택 제공.
- ABR 미확인: 약 1.5Mbps라는 기억의 정확성, 제한 후 지연 분포·기기 증상 감소율, 서버 인코딩·플레이어 설정의 세부 기여 범위. 서버 배경과 측정 기록 틀은 `docs/ABR_RECALL.md`에 정리했습니다. 이 설명을 실제 수행 이력으로 바꾸지 않습니다.
- 원본의 물음표 있는 정책과 HTTP 코드 의미 차이는 확정하지 않습니다.
- 도표는 담당 영역을 중심으로 재구성한 개념도입니다. 실제 네트워크 토폴로지와 다릅니다.
- 사례 02의 이전 Canvas 차트는 더 이상 상세 페이지에 노출하지 않습니다. ABR·LL-HLS의 지연과 VOD 시작 대기 시간 지표를 섞지 않습니다.

| 재현 | 입력, 전환 순서, 회전/리사이즈 조건 |
